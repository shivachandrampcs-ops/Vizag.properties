# Self-Service Property Listing (Builder / Owner / Agent)

This document describes the feature added on top of the original builder-only
system, how the data model was extended, and how to operate it.

---

## 1. Architectural decision

**The existing `builders` table is now the single "account" table for every
seller** — builder, property owner and real-estate agent.

| Before | After |
| --- | --- |
| `builders` = builders only | `builders` = all sellers, differentiated by `publisher_type` |
| `properties.builder_id` → builder | `properties.builder_id` → the owning seller (unchanged column) |
| One builder dashboard | One seller dashboard (`/dashboard/seller`) for all three types |

**Why extend instead of creating new tables (`owners`, `agents`, `users`)?**

* No data migration: every existing builder row keeps its id, password hash,
  properties and leads (`properties.builder_id`, `leads.assigned_builder_id`,
  admin screens and queries are untouched).
* No duplicated CRUD: one property form, one property service, one API surface.
* Backwards compatible: existing sessions, URLs and the admin UI keep working.

Only labels change per account type (e.g. *Property Owner* instead of
*Builder*, "Company (optional)" instead of "Company / Business Name").

## 2. Data model changes (additive only)

### `builders` (+ 7 columns, 2 indexes)

| column | type | notes |
| --- | --- | --- |
| `publisher_type` | enum `builder\|owner\|agent` | **default `builder`** → existing rows unchanged |
| `company_name` | varchar(200) | company / agency name (optional for owners) |
| `whatsapp_number` | varchar(20) | shown as a WhatsApp CTA on the listing |
| `locality` | varchar(120) | |
| `city` | varchar(100) | |
| `verified_at` | timestamp | set when an admin verifies the account |
| `verified_by` | int → admins.id | which admin verified it |

### `properties` (+ 7 columns, 2 indexes)

| column | type | notes |
| --- | --- | --- |
| `moderation_status` | enum `draft\|pending_review\|approved\|rejected` | **default `approved`** → existing listings stay live |
| `rejection_reason` | text | shown to the seller with an "Edit & Resubmit" action |
| `submitted_at`, `reviewed_at`, `published_at` | timestamp | moderation timeline |
| `reviewed_by` | int → admins.id | |
| `approval_info` | varchar(500) | free-text legal / approval information |
| `contact_preference` | enum `call\|whatsapp\|both` | drives the CTAs on the public page |

### `property_images` (+ 6 columns)

`provider`, `public_id`, `width`, `height`, `bytes`, `format` — needed to store
and later delete real uploaded assets.

### Availability vs moderation (kept separate, on purpose)

* `properties.status` = **availability**: `ready_to_move` / `under_construction`
  / `new_launch` / `resale` — unchanged.
* `properties.moderation_status` = **workflow**: `draft` / `pending_review` /
  `approved` / `rejected`.

A listing is public when `is_active = true AND moderation_status = 'approved'`.

### Migration

`drizzle/0001_self_service_listing.sql` (generated by `npm run db:generate`):

```bash
npm run db:migrate      # applies 0000 + 0001
```

The migration is **non-destructive** (only `CREATE TYPE`, `ADD COLUMN`,
`ADD CONSTRAINT`, `CREATE INDEX`) plus an idempotent back-fill:

```sql
UPDATE properties SET moderation_status='approved',
                      published_at = COALESCE(published_at, created_at)
WHERE published_at IS NULL;
UPDATE builders SET publisher_type='builder' WHERE publisher_type IS NULL;
```

`npx drizzle-kit push` also still works if you prefer it.

## 3. User flows

### Public

1. **"List Your Property"** CTA — navbar (desktop + mobile), homepage CTA band,
   properties page hero and the footer → `/list-your-property`.
2. Pick **I am a: Builder / Property Owner / Real Estate Agent** → `/register?type=…`
3. Fill: Full Name, Company/Business Name, Email, Mobile, WhatsApp, Password,
   Address, City, Locality (+ account type). No other personal data is asked.
4. Land straight in the dashboard (session is created on registration).

### Seller dashboard (`/dashboard/seller`)

Sections: **Dashboard · My Properties · Add Property · Leads · My Profile ·
Logout** + an account-type badge in the header (Builder / Owner / Agent and a
✓ when verified).

* Dashboard shows counters per moderation state (drafts / pending / published /
  rejected).
* My Properties shows the moderation chip and, when rejected, the admin's reason
  with an **Edit & Resubmit** action.
* Add Property reuses the existing property form with:
  * Basic info, Pricing & Area, Location (+ Google-Maps helper), **Legal &
    Approvals** (RERA ID, approval info), **Amenities & Highlights**,
  * **Contact Preference** (call / WhatsApp / both),
  * **Property Photos** — real uploads (see §4),
  * **Save as Draft** and **Submit for Review**.

### Admin

* **Property Approvals** (`/dashboard/admin/approvals`) — title, submitted by,
  account type, contact details, location, price, submitted date, moderation
  status; actions **View · Edit · Approve · Reject (with reason) · Unpublish ·
  Delete**, with tabs for Pending / Drafts / Rejected / Approved / All and a
  search box. The pending counter also appears in the sidebar.
* **Users & Verification** (`/dashboard/admin/users`) — every account with its
  type, property count and **Verify / Unverify / Activate / Deactivate**
  toggles.
* Existing **Properties**, **Leads** and **Dashboard** screens now also show the
  account type and moderation status.

### Moderation rules

| Who | Action | Result |
| --- | --- | --- |
| Seller | Save as Draft | `draft` (not public) |
| Seller | Submit for Review | `pending_review`, `submitted_at = now` |
| Seller | Edit an **approved** listing and re-submit | stays `approved` (live listings are not de-listed for typo fixes; the admin can reject/unpublish) |
| Seller | Edit a **rejected/draft** listing and submit | `pending_review`, reason cleared |
| Admin | Approve | `approved`, `published_at = now`, visible publicly + in the sitemap |
| Admin | Reject | `rejected` + mandatory reason, hidden from the public, reason shown to the seller |
| Admin | Unpublish | keeps `approved` but `is_active = false` |
| Admin | Create property | `approved` immediately |

## 4. Image uploads

* Route: `POST /api/uploads/property-images` (session required, 60 uploads/hour
  per account), `DELETE` to remove an asset.
* Production provider: **Cloudinary signed server-side upload** (`c_limit,w_1600`
  + `f_auto,q_auto` eager transformation). The API secret is only used to sign
  the request inside the route handler — **it never reaches the browser**.
* Dev-only provider: `UPLOAD_PROVIDER=local` **+** `ALLOW_LOCAL_UPLOADS=true`
  writes to `public/uploads`; it is refused when `NODE_ENV=production`.
* Browser: `src/components/image-uploader.tsx` —
  drag & drop, "Choose Photos" (opens the camera/gallery on mobile), multi-file,
  thumbnails with per-file progress, remove, drag-to-reorder (plus ← → buttons
  for touch), "set as cover", max 12 images, type/size validation, and
  client-side compression (`src/lib/image-compression.ts`: EXIF-aware decode,
  longest edge ≤ 1600px, WebP/JPEG re-encode, original kept if it is smaller).
* Server validation: ≤ 8 MB, JPEG/PNG/WebP/AVIF **magic-byte sniffing** (a
  renamed file cannot sneak through), URL whitelist (`http(s)` or relative) for
  pasted URLs.
* `syncPropertyImages()` deletes assets from the provider when a photo is
  removed or a property is deleted.
* `next.config.ts` allows `res.cloudinary.com` through `next/image`.
* Nginx already has `client_max_body_size 20M` (see `DEPLOYMENT.md`).

## 6. Notifications (extension point)

Email/WhatsApp are **not** required and are therefore not wired to a provider.
Every place that would notify someone calls `notify(event, payload)` in
`src/lib/notifications.ts`:

| Event | Triggered when |
| --- | --- |
| `registration` | a new seller account is created |
| `property_submitted` | a seller submits a listing for review |
| `property_approved` | an admin approves a listing |
| `property_rejected` | an admin rejects a listing (payload carries the reason) |
| `new_lead` | a buyer enquiry is created |
| `account_verified` | an admin verifies an account |

Adding a provider later = implement the commented `switch` in that file (or add
an in-app notification centre reading the same events). No call sites change.

## 7. Security notes

* **Ownership is enforced server-side**: `assertOwnership()` /
  `getOwnedProperty()` in `src/lib/property-service.ts` scope every seller
  route to the session account — another seller's property id returns `404`
  (no IDOR, no information leak). Ownership is never taken from the request body.
* Seller write payloads are validated with `propertyPayloadSchema`; the owner id,
  moderation status, verification flag and active flag can never be set by the
  client.
* Admin-only routes (`/api/admin/**`) go through `requireAdmin()`; every admin
  page through `requireAdminPage()`; every seller page through
  `requireSellerPage()`.
* Uploads require a session, are rate limited, size-limited and content-sniffed.
* Registration and login are rate limited per IP; session cookie is `httpOnly`,
  `sameSite=lax`, `secure` in production.
* Passwords are bcrypt(10); the JWT is signed with `AUTH_SECRET`.
* Public pages only ever query `is_active AND moderation_status='approved'`
  (`PUBLIC_PROPERTY_CONDITIONS` in `src/lib/queries.ts`), including the sitemap
  and the lead endpoint (enquiries for non-public listings are refused).
* Dashboard / login / register pages send `noindex, nofollow` and are disallowed
  in `robots.txt`.
* The "Verified" badge is driven by `builders.is_verified` (admin-controlled)
  only — the previous `projectsCount > 0` heuristic was removed.
* `drizzle.config.json` (which contained a hardcoded connection string) was
  deleted and replaced by `drizzle.config.ts`, which reads `DATABASE_URL` from
  the environment.

## 9. Local verification

```bash
cp .env.example .env
# set DATABASE_URL + AUTH_SECRET, and for uploads without a Cloudinary account:
#   UPLOAD_PROVIDER=local
#   ALLOW_LOCAL_UPLOADS=true
npm install
npm run db:migrate          # or: npx drizzle-kit push
npm run dev
open http://localhost:3000/api/health   # auto-seeds admin + demo builders
```

Then:

1. `/list-your-property` → register as **Owner** → land in the dashboard.
2. **Add Property** → upload 2–3 photos (drag them in or use the picker),
   set a cover photo, reorder, remove one, **Submit for Review**.
3. Log in as the seeded **admin** (`admin@vizag.properties` / `Admin@123`) →
   **Property Approvals** → Approve → check the listing on `/properties`.
4. Reject another one with a reason → log back in as the seller → the reason is
   shown → Edit & Resubmit → back to Pending Review.
5. **Users & Verification** → Verify an account → the public listing now shows
   the green *Verified* badge.

## 10. Known limitations / future improvements

* Notifications are logged, not delivered (see §6).
* Admin accounts are still seeded; there is no self-service admin signup.
* Because the root layout streams its shell early, `notFound()` pages (including
  non-approved listings) render the 404 page with a `200` status (soft 404).
  This is pre-existing behaviour; fixing it means removing the `<Suspense>`
  around `<GoogleAnalytics />` in `src/app/layout.tsx` (needs care because that
  component uses `useSearchParams()`).
* The rate limiter is in-process; move it to Redis if you run several PM2
  instances.
* Possible follow-ups: image reordering by drag on mobile is complemented by
  arrow buttons; bulk approve; per-property moderation history/audit log;
  document uploads for verification; SEO auto-review checklist.
